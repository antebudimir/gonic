# CI and Registry

Authoritative source for workflows, gating and registry targets. `05-git.md` and `08-upstream-sync.md` point here instead of restating it.

## Workflows

- `test.yaml` — lint + test, on `push: develop` and `pull_request`. Never runs on `master`.
- `release.yaml` — on `push: master` and on tags `v*`:
  - `test` — lint + test. Runs on master pushes and on tag pushes.
  - `release-please` — creates a GitHub release from `CHANGELOG.md`; needs `[test]`.
  - `build-binaries` — uploads release binaries; needs `[release-please]` and only runs when `release_created`.
  - `build-docker` — 4-arch image (amd64, arm64, armv6, armv7) to ghcr and Docker Hub; needs `[release-please]`, only when `release_created`.
  - `build-docker-tag` — 2-arch image (amd64, arm64) to ghcr; runs on any `refs/tags/v*`, with **no** `needs:`.
- `nightly-release.yaml` — cron + `workflow_dispatch`: `check-date` → `test` → `build-docker` (4-arch, ghcr + Docker Hub).

## What green actually proves

- `build-docker` green: compiled, linted, tested. The image itself is never exercised.
- `build-docker-tag` green: compiled and linted only — it has no `needs: [test]`. This is the job that fires for fork tags.
- Therefore a fork tag publishes an image that CI has not tested. Run the gates locally first (`03-workflow.md`); the tag job is packaging, not validation.

## Registries

- Fork tags (`vX.Y.Z-fork.N`) publish **ghcr.io only**, via `build-docker-tag`.
- Docker Hub pushes exist only in `build-docker` (release.yaml) and `nightly-release.yaml`, both of which are gated on `test` and/or `release-please`.
- `release-please` never fires on this fork (it needs upstream-shaped release commits), so on a fork tag there is no GitHub release, no binaries, and no Docker Hub push.
- Never add a push target under `sentriz/*`.

## Secrets

- `CR_PAT` — release-please token, release asset upload, and ghcr login (`${{ github.actor }}` + `CR_PAT`).
- `GITHUB_TOKEN` — Actions-provided; can check out and read the repo, but cannot write package artifacts without the package↔repo link and elevated scope. Use `CR_PAT` where a write is needed.
- `DOCKERHUB_USERNAME` + `DOCKERHUB_TOKEN` — Docker Hub login in `build-docker` and `nightly-release.yaml`.
- `IRC_NOTIFY_URL` — optional; the notify step is wrapped so a missing secret does not fail the run.

## Tag rules

- Tag only a commit whose gates passed; the tag publishes an image immediately.
- After pushing a tag, confirm the run actually started in the Actions tab. Path filters are not evaluated for tag pushes, but runs can still fail to appear; re-run or re-tag rather than assuming it fired.
- Push one tag at a time: `git push origin vX.Y.Z-fork.N`, never `--tags`.

## Do not

- Remove `needs: [test]` from a job that publishes an image.
- Move `test` after `release-please`, or let `build-binaries` skip `release-please`.
- Add a registry login without a matching secret documented above.
